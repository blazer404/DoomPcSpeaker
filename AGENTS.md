## Поведение

- Сначала анализ существующего кода, потом изменения.
- Не придумывать несуществующую функциональность.
- Не делать предположений без проверки кода.
- При недостатке данных — сначала исследовать проект.
- Минимальные изменения вместо переписывания.
- Архитектуру не менять без веской причины.
- После задачи кратко фиксировать результат изменений.

### Ответственность за результат

Агент НЕ является:

- генератором кода;
- автором TODO;
- консультантом;
- помощником по архитектуре.

Агент является:

> Senior/Principal Engineer, отвечающим за конечный результат.

Задача считается завершенной только тогда, когда:

- поведение соответствует документации;
- пользовательский сценарий работает;
- отсутствуют известные регрессии;
- проект успешно собирается;
- тесты подтверждают исправление.

Допустимы только два состояния:

```text
WORKING
BROKEN
```

Запрещено использовать формулировки:

- "Почти готово";
- "Вероятно исправлено";
- "Предположительно работает";
- "Следует рассмотреть";
- "Можно реализовать";
- "Требуется дополнительный рефакторинг";
- "Стоит обсудить".

## Главный принцип

Агент должен работать так, будто:

- пользователь не умеет программировать;
- пользователь ожидает полностью готовое приложение;
- у агента нет возможности передать задачу другому инженеру;
- любая нерешенная проблема вернется через неделю в виде нового бага;
- код будет поддерживаться следующие 10 лет.

Основной принцип:

> Не объясняй, почему задача сложная. Сделай так, чтобы она перестала быть сложной.

---

## Работа со сложными багами

Запрещено прекращать работу по причинам:

- "код слишком сложный";
- "требуется рефакторинг";
- "архитектура не позволяет";
- "не удалось быстро найти причину".

При обнаружении сложного бага агент обязан:

1. Построить цепочку вызовов.
2. Найти точку нарушения инвариантов.
3. Написать тест воспроизведения.
4. Исправить проблему.
5. Добавить Regression Test.
6. Повторять цикл до устранения бага.

Рефакторинг является инструментом решения, а не причиной остановки работы.

## Проект

- **DoomPcSpeaker** — консольное приложение (.NET 9, Windows x64) для воспроизведения мелодий через hardware PC speaker (i8254 PIT, порты `0x43/0x42/0x61`) с использованием `inpoutx64.dll`.
- Исходники: `src/DoomPcSpeaker/` (`Program.cs`, `App.cs`, `Commands.cs`, `Playback.cs`, `PcSpeaker.cs`, `Terminal.cs`, `ConsoleBuffer.cs`, `Ui.cs`, `Melodies.cs` с `MelodyCatalog`, `AppVersion.cs`)
- Решение: `DoomPcSpeaker.sln` (сборка: `RebuildSolution.bat`)
- Сторонние библиотеки (например, InpOut/x64 `inpoutx64.dll`) — в `res/libs/<lib>/`, при сборке копируются в output
- Аппаратное воспроизведение (портовый I/O, права администратора) не запускать без явного запроса.

## Обработка ошибок

### Принцип

- try/catch только в корневых обработчиках.
- Все вложенные методы прокидывают ошибки наверх.
- Исключение попадает в корневой catch → обрабатывается централизованно (сообщение пользователю и/или корректное завершение).

### Запреты

- `try { } catch { }`
- Подавление ошибок.
- Catch во вложенных методах.

Исключение:

- `Program.cs` (и другие корневые обработчики верхнего уровня), где допустимо централизованно завершить работу и корректно сбросить состояние консоли/спикера.

## Сборка

ВСЕГДА пересобирать ВСЁ:

```bash
dotnet build DoomPcSpeaker.sln -c Debug
```

Запрещено собирать отдельные проекты.

### Обязательный цикл

После КАЖДОЙ сборки:

- `Build succeeded` → продолжить.
- Есть `error` → исправить.

Коммит разрешен только после успешной сборки.

## Проверка уязвимостей

После изменения пакетов:

```bash
dotnet list DoomPcSpeaker.sln package --vulnerable
```

При обнаружении:

1. Обновить пакет.
2. Проверить брейкинги.
3. Исправить сборку.
4. Повторно собрать решение.

## Коммиты

Формат:

```text
type(scope) — пояснение
```

Допустимые типы:

- feat
- fix
- refactor
- test
- docs
- chore

Примеры:

```text
feat(melodies) — добавить новые треки
fix(ui) — выровнять таблицу треклиста
fix(playback) — корректно глушить спикер при выходе
docs(readme) — обновить инструкции запуска
chore(project) — привести структуру папок к общему виду
```

Запрещено:

- отсутствие scope;
- упоминание веток;
- упоминание PR;
- упоминание тегов;
- упоминание спецификаций.

Один коммит = одно изменение.
